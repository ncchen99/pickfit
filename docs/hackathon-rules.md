## 2. 一定要做

| 規則 | 說明 |
|---|---|
| **使用 Meta 的模型** | 第一輪評審是 pass/fail，會檢查有沒有「合理地」使用。可用：透過 Meta Model API 的 Muse Spark 系列、Muse Wonder、Muse Image、Muse Voice Transcribe、SAM 3.1；開放權重的 Muse Glimmer、Muse Spark Open；寫程式用的 Muse Code coding agent |
| **符合題目之一** | 「Build for Your World」：把 Meta 模型帶進你熟悉的領域，解決親身遇到的問題。「Push the Frontier」：用在軟體、機器人、製造、能源、材料等領域的前沿挑戰 |

## 3. 不能做

- **違反法律、倫理或平台政策**的專案。
- **使用沒有權利的程式碼、資料或素材**。第三方套件、圖片、資料集都要確認授權。
- **官方列出的「反面範例」**（太常見或違反政策），包括：
  - 任何用 AI 給醫療建議的專案（心理健康顧問、皮膚瑕疵偵測等）
  - **基本的 RAG 應用**
  - 簡單的圖片分析器
  - 簡單的「AI 教育」聊天機器人
  - AI 履歷篩選
  - AI 營養教練
  - 人格分析
  - 運動分析或教練
  - 任何政治或戰爭相關的專案
- 重複報名、假身分會被取消資格。

## 4. 評分方式

1. **第一輪（pass/fail）**：是否合理符合題目，並在比賽中合理使用了 Meta Model API 或 Meta 開放權重模型。
2. **第二輪（0–10 分）**：

| 項目 | 權重 | 評審在看什麼 |
|---|---|---|
| Impact | 30% | 真實世界的潛力、誰受益、會不會真的有人用、是否符合題目 |
| Use of Meta AI Tooling | 25% | 用法有沒有創意、是否超越基本串接、有沒有展現讓 Meta 也意外的能力 |
| Technical Depth & Execution | 20% | 工程是否扎實、是否經過細心打磨 |
| Demo | 25% | demo 能不能動、現場撐不撐得住、影片好不好看 |

3. **第三輪**：每組前 5 名進入決賽，評審現場看影片並用同一套標準排名。

- **報名表已交過專案構想**。主辦方本來就預期參賽者在開賽前有構想；問題只在賽前的「成果」有沒有和比賽作品分開、標清楚。

## 9. 給之後的 agent：工作守則

1. **不要竄改任何時間紀錄。** 不要改 commit 時間、不要 rebase 改寫歷史、不要改檔案時間，也不要把賽前資料寫成比賽期間的成果。規則要求的是「標清楚」，不是「看不出來」。
2. **所有程式碼都在開發期間（10/27 – 11/4 ET）內寫並 commit。** 不要從別的專案整段複製舊程式碼；真的要用，要在 README 註明來源與授權。
3. **Commit 要小而頻繁、訊息寫清楚做了什麼。** 這份歷史就是「哪些是比賽期間做的」的證據。
4. **新增第三方套件、資料、圖片前先確認授權**，並記在 README 或 `NOTICE`。
5. **不要把 API key 或 credits 相關資訊 commit 進來**；用 `.env` 並確認已在 `.gitignore` 中。
6. **交件前跑一次第 11 節的檢查表。**
7. **參與製作的人只能是已核准的參賽者。** 不要把未核准者的貢獻放進來。

## 10. 建議做法

- **把 Meta 模型放在產品的核心，而不是外掛。** 「Use of Meta AI Tooling」佔 25%，而且第一輪就會檢查。例如：用 Muse Spark 當推薦 agent 的大腦；用 Muse Voice Transcribe 實測語音輸入類軟體，正好對上第一個類別（桌面語音輸入）；開發過程用 Muse Code。
- **避開「基本 RAG 應用」的印象。** 「查資料庫再回答」很容易被歸到反面範例。重點放在 agent **實際幫人裝好、設定好、確認能用**，以及把真實使用結果回收回來，這也是本專案和現有對手的差異。
- **瞄準 Best Agentic Use-Case。** 「選軟體、安裝、設定、驗證」本身就是多步驟的 agent 流程，跟這個獎的評審重點相符。
- **可考慮順便拿 Best Build on Meta Open Weight Models**：若有一條路徑用 Muse Spark Open 或 Muse Glimmer（透過 Baseten 或 Modal），提交時標記出來。
- **題目選「Build for Your World」**：繁中使用者、台灣開發者找不到合適軟體，是團隊親身遇到的問題。
- **Demo 影片的結構**：**開頭第一句**說明賽前有什麼、這週做了什麼（官方 FAQ 的要求），例如「賽前我們只做了使用者研究與規劃，影片中的所有程式與功能都是這週做的」。接著用 15 秒講問題，再實際操作「agent 推薦並裝好軟體」的完整流程。
- **交件後在 X 發 demo 貼文**，可同時參加 Most Viral 與 Community Vote。
- **組別已定：Indie Developer，個人參賽**（見 [brief.md](brief.md) 第 14 節）。
