# GUI 與網頁 App 的易用性評分：合併提案

## 1. 一句話結論
以 Design 3（從人和產品出發）為基底。做法是讓 Muse Spark 1.3 看 pickfit 自己拍下的畫面和操作紀錄，照固定檢核表打分。每一分都要引用畫面上的字，而且 OCR 或 DOM 要找得到這些字。只有 app 自己造成的問題才扣分。易用性會算進桌面和網頁 App 的品質分（公式 gui.v1、web.v2）。要當寶藏，必須「有實際操作，而且易用性 ≥70」。

另外從兩份設計各取一部分：
- 從 Design 2 取：「第一眼」和「使用中」分兩次呼叫、每個卡關都要歸因、程式設的上下限、不把名字給模型看。
- 從 Design 1 取：先把證據搬到安全的地方；量得到的數字只顯示，不計分。

影片段落和網頁錄影已經有兩個 session 在做，這份計畫不重做，只把每條發現連到影片的段落時間。

我讀程式和資料查核的結果：
- **念誠說的問題是真的**：tool-page-ux 分支的 web.v1 公式下，58 個操作過的網頁有 51 個 ≥80，網頁寶藏有 42 個。
- **影片段落已經有了**：tool-page-ux 的 `2cfedb82` 已經有段落播放器。confident-einstein 的 `371f2248` 會產生 GUI 影片段落，另外還有尚未 commit 的 `web_video.py`（第二次造訪網站、不用模型重播、錄下網頁畫面）。Design 1 說「沒有任何段落程式」，這已經過時。
- **操作數字雜訊很大**：concessio 點輸入框只是讓它取得焦點，畫面本來就不會變（紀錄是 `changed=false`）。開檔對話框在 Xvfb 卡到 28 步上限，是環境問題。`seconds_to_window` 記成 0.0。所以動作數這類數字只顯示、不計分。

## 3. 怎麼併入現有分數與排序
- **易用性（0–100）**：各維度分數除以 2 後加權平均，只算有分數的維度。權重：一打開就能用 20、功能找得到 30、操作有回應 25、看起來舒服 25。使用中合計 55，比第一眼的 45 重。
- **只看了第一個畫面時**（沒有通過的操作），易用性最多算 0.6。這和「只啟動」在沙盒驗證只拿 0.6 是同一個道理。
- **gui.v1**（desktop_app 而且有 GUI run）：沙盒驗證 25、易用性 30、安裝文件 15、維護 8、工程習慣 4、回應速度 8、使用回報 10+。
- **web.v2**（web_app）：沙盒驗證 25、易用性 35、瀏覽器事實 30（不變）、使用回報 10+。
- **寶藏門檻**：桌面和網頁 App 另外要「有實際操作的 run，而且易用性 ≥70」，寫進 `Scores._check_treasure`。
- **沒有資料的維度**：照舊不算進分母，信心降低。分數上限不變（未驗證的最多 69）。
- **例子**：今天操作過的網頁，品質中位數是 87.3。改用 web.v2 後（瀏覽器事實 0.8），易用性 0.55 會落在約 76，易用性 0.85 約 88。
- **不變的部分**：CLI、TUI、MCP、server_daemon、self_hosted_web_app，以及沒有 GUI run 的桌面 App，都維持 b3.v5，也沒有易用性欄位（是沒有，不是 0）。
- `refresh_scores` 會重用已存的文件評分和易用性評審（用 inputs_sha 判斷有沒有變），不必重打模型。
- **排序**：適合度優先。適合度相近時，偏好易用性較高的 App，並把一條卡關寫進取捨說明。不拿有易用性分數的 App 和沒有的比。

## 4. 頁面與 agent 回答怎麼呈現
**工具頁**（tool-page-ux session 負責排版，這邊提供資料）：
- 影片下方新增一塊「用起來如何（pickfit 實際操作）」。第一行寫依據，例如：「pickfit 在沙盒（Linux Xvfb 1280×800、沒有視窗管理器）操作了 3 個功能；Muse Spark 1.3 照固定檢核表看了 7 張畫面，兩次結果一致。」
- 每個維度一列，有三格刻度、一個判語（容易上手／有些卡關／不好上手），再列一到兩條發現，並引用畫面上的字。
- 每條發現都連到影片時間：點「▶ 0:22」就用現有段落播放器的 `data-seek` 跳過去。剪掉的片段改連到原始錄影的時間；沒有影片就給截圖裁切並畫框。
- 只看了第一眼的 App，寫「只看了第一個畫面」，不給總分。
- 固定加一行：「沒檢查：螢幕閱讀器、只用鍵盤、手機」。操作員或環境造成的卡關列在折疊的「pickfit 怎麼測」裡，不藏起來。

**影片段落**：由 confident-einstein（產生段落、網頁錄影）和 tool-page-ux（播放器）負責。段落名稱只來自 pickfit 的紀錄和 usage_guide，而且只標通過的功能。這份計畫只加一個 `moment_of`，把原始錄影的時間換算成剪輯後影片的時間。

**Agent（MCP）**：
- `find_software`、`get_install_guide` 加一個選填的 `ease_of_use` 物件：分數（可為 null）、依據、判語、各維度、最多 3 條附觀看連結的發現、沒檢查的項目，再加上段落列表。
- 伺服器說明要求 agent 說「這是 pickfit 的 AI 操作員在沙盒裡的實測」，不是使用者評價；最多引用一條發現；CLI 不提易用性。
- MCP 輸出格式（zod）在同一個 commit 更新，GUI 和網頁各加一個 MCP 測試，避免再發生 11/2 那次 `action_checked` 讓 `find_software` 出錯的事。

## 5. 校準：念誠怎麼人工評幾款來檢查
- **挑 12 款**，用 sha256(slug) 加種子照規則抽，種子寫進 commit：
  - 已有影片的 GUI 4 款（concessio、nip4、breaktimer-app、neon-vision-editor）
  - 只啟動過的 GUI 2 款（Linux、macOS 各 1）
  - 操作過的網頁 3 款
  - 只到 install 的網頁 1 款
  - 「好看但難用」探針 2 款：操作卡到步數上限或放棄、但畫面乾淨的
- `scripts/ease_sheet.py` 在本機產生盲評頁。頁面上只放模型看到的畫面、影片段落、操作目標和同一份評分標準，不顯示 pickfit 的分數。網頁 App 念誠可以自己實際點兩分鐘。
- 念誠每款要評：各維度 0/1/2 或「看不出來」、整體 1–5、自己會不會用。大約 40 分鐘。結果存在 `data/calibration/ease-ratings.yaml`，不放在 eval/。
- **通過標準在念誠評之前先 commit**：
  - 每個維度，12 款中至少 10 款和念誠差距 ≤1 級
  - 念誠的整體分數和 pickfit 易用性的 Spearman ≥0.5
  - 兩個探針的易用性都 ≤50
  - 沒有任何一款差到兩個判語等級
- 允許修改一次評分標準或 prompt（不加分數偏移），然後同樣 12 款重跑。還是不過，就改成「只顯示，不計分，也不進寶藏門檻」。
- 同時回報這幾個數字：1.3 自己兩次的一致度、Muse Spark Open 的交叉一致度、易用性和知名度的相關（|rho| 應 ≤0.3）、同一款 App 在 Linux 和 macOS 的分差。之後凍結為 ease.v1。

## 6. 誠實規則
1. 只用 pickfit 在通過的 run 裡自己拍下的畫面和紀錄。不看開發者提供的截圖、README 行銷文字、星數、App 名稱。
2. 給 0 以上的分，都要引用畫面和框，以及畫面上的字，而且 OCR 或 DOM 要找得到這些字，否則該項記 null。低於 2 分時，也要指出是哪個 app 造成的卡關。
3. 只有 app 造成的問題才扣分。沙盒的限制（沒有視窗管理器、沒有 GPU、缺字型、權限框、無頭 Chromium、固定解析度）會列出來，但不扣分。
4. 沒看到就寫沒看到：沒操作、評審意見不一致、畫面被沙盒弄壞，都寫成文字狀態，不補值、不當 0。
5. 用詞固定為「pickfit 的 AI 操作員在沙盒裡的實測」，不說「使用者覺得好用」。操作目標是 pickfit 探索後寫的，所以頁面註明「這是在有提示的情況下找得到」。
6. 每份評審都記下 run_id、inputs_sha（每張畫面的 sha256）、模型、日期、prompt 版本。畫面換了就清掉重評。
7. 影片照 video.py 的規則：整段、依序、加速有標示、只標兩次都通過的功能。網頁第二次造訪時重播沒通過，就不出影片，也不改等級。
8. 沒有廣告、不看知名度；所有 App 用同一套 prompt。formula_version 寫 gui.v1／web.v2，舊分數只能透過 refresh 改動。

## 10. 風險
- **AI 操作員不等於人**：Muse Spark Open 會點偏，在 Mac 上會偏幾十像素。如果歸因錯了，「功能找得到」量到的其實是操作員。對策：歸因時要引用畫面、只扣 app 的、取樣兩次、校準時一併檢查歸因。
- **涵蓋的 App 不多**：GUI 只有 14 筆有通過的操作，87 筆只有第一眼，而 11/3 12:00 之後就不再操作新的 App。
- **沙盒畫面失真**：Xvfb 缺視窗管理器和字型，Linux 版可能看起來比 macOS 版差。對策：這類畫面記 null，並比對同一款 App 在兩個平台的分差。
- **模型偏好好看的介面（月暈效應）**：對策是兩次呼叫分開、使用中只能引用操作畫面、加兩個探針、使用中的權重大於第一眼。
- **1.3 一次能不能收 6–8 張圖還沒試過**：不收就拆開呼叫，費用約多 30%。
- **網站畫面上的文字可能夾帶指令**：prompt 寫明那只是資料，而且標籤要被 OCR 或 DOM 對得上。
- **demo 前分數會變動**：寶藏數會下降，demo 候選排名也可能變；發布前要重跑候選檢查。
- **合併衝突**：schema.py 的 RunVideo、video.py、tool.ts 三個分支都在改，要先約定各欄位歸誰。
- **證據只放在 worktree 的 runs/**：worktree 一清掉就無法追溯，所以第一步就要搬。
- **MCP 輸出格式漏改**：會讓 `find_software` 出錯。要在同一個 commit 一起改，並且發布後在線上實際打一次。
