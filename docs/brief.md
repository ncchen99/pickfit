# 任務指示：這次黑客松要做什麼

2026-10-28 · 給接手的 agent 與團隊成員。動手前先讀這份，再讀 [hackathon-rules.md](hackathon-rules.md)。

**一句話**：在 AI coding agent 讓每個人都能做軟體的年代，好軟體多到沒人找得到。我們要做一個**不屬於任何一家的軟體顧問**，主動把默默無聞、但品質好的軟體找出來、驗證過、整理好，讓任何人的 AI agent 都能推薦、安裝並帶人上手。

---

## 1. 為什麼做這件事

**現象**：vibe coding 讓做軟體變得很便宜，獨立開發者、學生、小新創每天都在 GitHub 放出新作品，在 Threads、Facebook、X 上分享。軟體的數量爆炸，但「找到適合自己的那一款」反而更難。

**卡在哪裡**：
- **找不到**：搜尋和廣告的排序反映的是誰會行銷，不是誰最適合你。好作品沉在 GitHub 裡，名字取得隨意，也沒在宣傳。
- **agent 也不認識**：模型的訓練資料有截止日，今年才出現的專案多半不在裡面。agent 自己上網查，找到的也還是行銷最強的那幾個。
- **裝不起來**：就算找到了，小專案常常缺文件，正確的安裝方式與設定只有作者知道。

**現有平台補不到這一塊**：有名的軟體已經被整理得很好。G2、Capterra 這類評論站，Toolradar 這類已有 MCP 的工具目錄（上萬款工具），還有 ChatGPT 自己的 plugin 目錄，都以知名的商業 SaaS 為主，營收也多半來自廠商。**高品質、但默默無聞的長尾軟體**，沒有人在系統性地收。

**一個真實的例子（團隊成員的親身經驗）**：為了找一個好用的語音輸入工具，花了半個月比較各種替代品，最後是在 GitHub 動態牆上偶然點開朋友做的 App，才發現它就是要的：準確、即時，背後用的語音模型價格只有大廠的十分之一。但直接搜尋「最新語音辨識服務」，幾乎找不到它。**好東西早就存在，只是沒有一條路通到使用者這裡。**

---

## 2. 方向調整：從「繁中語音輸入」到「全球的寶藏軟體」

賽前的規劃把第一步鎖定在「台灣開發者的繁中桌面語音輸入」。為了這次 Meta 黑客松，這個範圍**太窄、太在地**，改成：

| | 賽前的規劃 | 黑客松的目標 |
|---|---|---|
| 使用者 | 台灣開發者，10–20 人 | 全球使用 AI agent 的人 |
| 軟體範圍 | 一個類別（語音輸入），手寫 15–40 筆 | 不限類別，重點是**默默無聞但品質好**的軟體 |
| 資料怎麼來 | 人工手寫、逐筆查證 | **agent 自動發現、讀懂、實際驗證**，人工抽查 |
| 核心價值 | 推得比 agent 自己查更準 | 找到 agent 自己找不到的，而且確認裝得起來、用得了 |

**保留不變的核心理念**：
- **我們是知識，不是手。** agent 負責執行指令、安裝、操作；我們負責告訴它該用哪個、怎麼裝、怎麼上手。打個比方：我們不做導航 App，我們做地圖資料。
- **推薦是配對，不是排名。** 沒有「最好的軟體」，只有「最適合你的」：作業系統、預算、隱私（能否本機執行）、語言、工作流程都不同。
- **中立。** 不屬於任何一家 agent 生態系，所以可以推薦大廠不會主動推薦的選項，包括「你不需要付費」與「內建的就夠了」。
- **看結果，不只看評論。** 最可信的訊號是「裝了沒、還在用嗎、換成什麼」，不是星數或五星評論。

## 3. 願景

> **好軟體靠實力被找到，也養得活做它的人。**

如果「發現」這件事被解決，軟體的競爭方式就會改變：贏的不再是行銷預算最多的，而是最用心、最替使用者著想的。對獨立開發者來說，這是第一次不必會行銷，作品也能被需要的人找到。

## 4. 黑客松要交出的東西

八天內做出一條能 demo 的完整路徑：**發現 → 讀懂 → 驗證 → 配對 → 安裝 → 回報**。

### 4.1 發現 agent（Discovery）

從公開來源收集「可能是好軟體」的訊號，交給 Meta 模型判斷與整理。

- **來源**（授權規則見第 8 節）：GitHub（新建的 repo、topic、release、awesome 清單）、Hacker News 的 Show HN（官方 API）、Homebrew 與 winget 的套件資料，以及 Threads、Facebook 上的分享（只走官方 API 或使用者提交的連結，**不爬網頁**）。
- **Meta 模型做的事**：讀 README、貼文、截圖，判斷「這是不是一個可以拿來用的軟體」，並抽出結構化的檔案：做什麼、適合誰、平台、安裝方式、價格模式、是否本機執行、授權、最近更新。
- **提交入口**：任何人（包括作者本人）貼一個 GitHub 或 Threads 連結，幾分鐘內就變成可被推薦的軟體。這同時是供給端的成長方式，也符合「在社群分享作品」的習慣。

### 4.2 驗證 agent（Verification）——我們和別人最大的差別

**不只看描述，實際裝起來試。** 在沙盒環境裡照 README 安裝並執行，記錄：
- 裝不裝得起來、要幾步、卡在哪裡；
- 實際可行的安裝與設定步驟（這是 agent 自己最容易答錯、也最有價值的資訊）；
- 執行畫面的截圖，交給 Meta 的視覺模型判斷是否真的能運作。

驗證結果決定這款軟體能不能被推薦，也成為品質分數的一部分。

### 4.3 「寶藏分數」：品質與知名度分開算

- **品質**：驗證通過、文件完整度、維護是否活躍（最近 release、issue 回應）、真實使用者的提及與使用結果。
- **知名度**：星數、下載量、被搜尋到的難易度。
- **我們要找的是品質高、知名度低的那一群**，並在推薦時說明理由，不讓星數主導。

### 4.4 配對 MCP

一個 MCP server，讓任何 agent（Claude Code、Codex、其他 harness）都能查詢。先收斂到 4 個工具：

| 工具 | 做什麼 |
|---|---|
| `find_software` | 依需求與條件（OS、預算、隱私、語言）回傳 2–3 個最適合的選項，附理由與最好的免費選項 |
| `find_alternatives` | 找某個軟體的替代品；要求帶上「目前用什麼、哪裡不滿意」 |
| `get_install_guide` | 回傳在使用者系統上**經過驗證**的安裝與設定步驟，以及需要使用者手動完成的部分（例如權限授權） |
| `report_outcome` | agent 回報裝了沒、成功了沒、使用者是否滿意 |

agent 最多先問一兩個最能分辨選項的問題，其餘交給使用回饋。不需登入；回應裡不放推薦碼或廣告。

### 4.5 （可選）公開展示頁

一個簡單的網頁，列出系統最近發現並驗證過的寶藏軟體，每筆附「為什麼值得用」。用途是 demo、社群投票，以及讓開發者看到自己的作品被收錄。時間不夠就砍。

## 5. Demo 要錄下的那一刻

1. **使用者在自己的 agent 裡說**：「我想要一個 Mac 上、免費、能離線的 X 工具。」X 從第 14 節的兩個類別（開發者 CLI 工具、本地 AI／LLM 工具）裡，挑寶藏軟體確實比知名產品好的情境。
2. **對照**：同一個 agent 自己上網查，推薦的是知名但不合條件的產品，或今年才出現的好專案它根本不知道。
3. **接上我們的 MCP 後**：agent 推薦一個今年才出現、星數不多、但我們驗證過裝得起來而且好用的專案，說明理由，並附最好的免費選項。
4. **agent 照驗證過的步驟幫使用者裝好**，第一次執行就成功。
5. **供給端**：作者在 Threads 分享新作品，貼上連結後幾分鐘，它就被讀懂、驗證，出現在推薦結果裡。

影片開頭第一句要說明賽前有什麼、這週做了什麼（官方要求，見 [hackathon-rules.md](hackathon-rules.md) 第 7 節）。

## 6. Meta 模型怎麼用（評分 25%，第一輪必查）

Meta 的模型必須是產品實際運作的核心，不是外掛。開工前先查官方文件確認各模型的實際能力與名稱。

| 環節 | 模型 | 用途 |
|---|---|---|
| 讀懂與抽取 | Muse Spark（Meta Model API） | 讀 README、貼文、release notes，判斷是不是可用的軟體，抽出結構化檔案 |
| 驗證判讀 | Muse Spark 的多模態能力 | 看執行截圖，判斷軟體是否真的在運作；讀安裝錯誤訊息並嘗試修正 |
| 大量初篩 | Muse Spark Open 或 Muse Glimmer（開放權重，透過 Baseten 或 Modal） | 便宜地大量過濾候選 repo 與貼文；同時爭取「Best Build on Meta Open Weight Models」 |
| 配對 | Muse Spark | 把使用者的自然語言需求對到條件與候選，產生推薦理由 |
| （選用）影音 | Muse Voice Transcribe | 有些作者用影片介紹作品，轉成文字後一起讀 |

可以同時用非 Meta 的工具，但要讓評審一眼看出 Meta 模型在哪裡、做了什麼。README 要有一節專門說明。

## 7. 對照評分標準

| 評分項目 | 我們的答案 |
|---|---|
| Impact（30%） | 全球的獨立開發者與使用者；讓好軟體不必靠行銷也能被找到 |
| Use of Meta AI Tooling（25%） | 發現、抽取、視覺驗證、配對都由 Meta 模型驅動；開放權重模型做大量初篩 |
| Technical Depth（20%） | 沙盒中實際安裝驗證、品質與知名度分開計分、標準 MCP 介面 |

**加碼獎**：Best Agentic Use-Case（發現、驗證、安裝都是多步驟 agent 流程）、Best Build on Meta Open Weight Models（初篩用開放權重模型）、Most Viral 與 Community Vote（被收錄的開發者自己就會分享）。

**題目**：Build for Your World。這是團隊親身遇到的問題。

**要避開的印象**：「基本 RAG 應用」是官方列出的反面範例。我們的重點不是「查資料庫再回答」，而是**主動發現、實際驗證、帶人裝好**。demo 與 README 都要讓這點一眼看出來。

## 9. 不做的事

- **不自己做被推薦的軟體**：自己當裁判又下場比賽，會毀掉中立。
- **不放推薦碼、廣告或付費置入**。
- **不做帳號、金流、本機盤點工具**：都是長期構想，黑客松期間不做。
- **不碰醫療建議、政治、戰爭**相關的軟體推薦（官方禁止）。
- **不違反來源的使用條款**（見第 8 節）。
- **不把賽前資料複製進這個 repo**；需要時只取知識（見 [CLAUDE.md](../CLAUDE.md)）。

## 10. 怎麼證明有用

在比賽期間建立一份**全新的評測題組**（約 20 題），每題的最佳答案是一個不太有名、但確實更適合的軟體。題目在寫資料之前就先 commit 凍結，避免不自覺地照著題目準備資料。

比較兩組：
- **對照組**：同一個 agent 自己上網查，不接我們的 MCP。
- **實驗組**：同一個 agent 接上我們的 MCP。

逐題檢查：推薦的軟體是否存在且符合條件、安裝步驟是否正確、照做後能否成功執行。另外記錄系統面的數字：發現了多少候選、驗證通過率、從作者發文到可被推薦花了多久。結果（包括輸的題目）放進 README。

## 11. 建議的技術方向

接手的人可以調整，但改之前先想清楚理由。

- **MCP server**：無狀態，部署在 Cloudflare Worker 這類 serverless 環境，團隊熟悉、成本低。後端不一定要部署才能交件，但 demo 要能真的連上。
- **資料**：每款軟體一份 YAML（或 JSON），放在 git 裡當正本；事件記錄（查詢、回報）用一張簡單的表，不記 IP。
- **發現與驗證管線**：Python 腳本或 worker；沙盒可考慮 Modal 的 sandbox（合作夥伴有 credits）。
- **檔案欄位**：`slug`（永不改）、`name`、`summary`、`homepage`、`repo`、`platforms`、`install`、`pricing`、`open_source`、`license`、`processing`（local／cloud／hybrid）、`last_release`、`verification`（結果、步驟、截圖、時間）、`scores`（品質、知名度）、`sources`。
- **金鑰**：一律放 `.env`，不要 commit。

## 13. 風險

- **範圍太大**：「全球、不限類別」做不完，而且是一個人做。demo 只做兩個類別（見第 14 節），把整條路徑做深，比 20 個類別都做淺好。時間不夠時，依序砍：公開展示頁 → Threads 提交入口 → 開放權重初篩。
- **驗證很難自動化**：GUI 軟體、需要權限的軟體、只支援特定 OS 的軟體很難在沙盒裡跑。先從 CLI 與網頁工具做起，其餘標成「未驗證」，不要假裝驗證過。
- **品質判斷會被灌水**：開放提交一定有人刷。黑客松期間由驗證結果與人工抽查把關，並在 README 誠實說明。
- **已經有人在做目錄與 MCP**：差別要放在「找得到長尾」與「實際驗證」，不是「有 MCP」。
- **被看成基本 RAG**：見第 7 節。

## 14. 待決定

| 決策 | 結果 | 狀態 |
|---|---|---|
| 參賽組別 | **Indie Developer**。評審看創意、技術企圖心、能不能動 | 已定（2026-10-28） |
| 團隊成員 | **個人參賽**（念誠）。不要把其他人的貢獻放進來 | 已定（2026-10-28） |
| 對外名稱 | **pickfit**。交件、demo、README 都用這個名字；不要用「Software Advisor」（和 G2 旗下的 Software Advice 太像） | 已定（2026-10-28） |
| demo 的類別 | **開發者 CLI 工具**、**本地 AI／LLM 工具**（見下方說明） | 已定（2026-10-28） |
| 技術選型 | 照第 11 節 | 建議採用 |

**名稱查核（2026-10-28）**：`pickfit.dev`、`.app`、`.ai`、`.io` 在 RDAP 查不到註冊紀錄；GitHub 帳號、npm、PyPI 的 `pickfit` 都還沒人用；`pickfit.com` 已被註冊。網域隨時可能被搶，要用就盡早買。

**為什麼選這兩個類別**：
- **開發者 CLI 工具**：最容易在沙盒裡自動安裝與執行，驗證 agent 能真正跑起來；用 agent 的人最常需要；GitHub 上新專案最多。
- **本地 AI／LLM 工具**（本地模型執行器、推論伺服器、離線 AI 小工具等）：今年的新專案很多，模型的訓練資料多半不認識；也呼應 Meta 開放權重模型的主題。
- **語音輸入**等 GUI 軟體需要麥克風、輔助使用等權限，沙盒很難自動驗證，黑客松期間不當 demo 主軸；資料可以收，但標成「未驗證」。
