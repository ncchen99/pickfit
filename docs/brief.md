# 任務指示：這次黑客松要做什麼

2026-10-28（10/29 補上：重複造輪子的代價、使用者的渴望、收錄的兩條路、影片要講的問題與長期規劃、產品網頁改成必做；11/1 修訂：定位、GUI App 納入範圍、來源整合，見第 2.1 節）· 給接手的 agent 與團隊成員。動手前先讀這份，再讀 [hackathon-rules.md](hackathon-rules.md)。

**一句話**：在 AI coding agent 讓每個人都能做軟體的年代，好軟體多到沒人找得到。我們要做一個**不屬於任何一家的軟體顧問**，主動把默默無聞、但品質好的軟體找出來、驗證過、整理好，讓任何人的 AI agent 都能推薦、安裝並帶人上手。

---

## 1. 為什麼做這件事

**現象**：vibe coding 讓做軟體變得很便宜，獨立開發者、學生、小新創每天都在 GitHub 放出新作品，在 Threads、Facebook、X 上分享。軟體的數量爆炸，但「找到適合自己的那一款」反而更難。

**卡在哪裡**：
- **找不到**：搜尋和廣告的排序反映的是誰會行銷，不是誰最適合你。好作品沉在 GitHub 裡，名字取得隨意，也沒在宣傳。
- **agent 也不認識**：模型的訓練資料有截止日，今年才出現的專案多半不在裡面。agent 自己上網查，找到的也還是行銷最強的那幾個。
- **裝不起來**：就算找到了，小專案常常缺文件，正確的安裝方式與設定只有作者知道。

**結果：大家都在重複造輪子。** 軟體分散在各個角落，每個人都在做自己的版本，但很多時候已經有很棒、甚至更符合需求的軟體存在，只是沒被找到。自己做不是免費的：做完之後要一直維護，要花時間與金錢，現在還多了一筆 AI 的 token 費用。同樣的力氣一再花在同樣的問題上，已經存在的好成果卻沒被用到。

**換個方向看：使用者渴望的是什麼。** 上面是從問題看，也可以從渴望看，兩者是不同的面向。念誠自己在用的時候，會希望**有一個 AI 幫我找到合適的軟體，而不是什麼都自己來做**：說出需求，它就知道世界上已經有哪些好東西、哪一款最適合我、怎麼裝好；我把時間花在真正想做的事上。傳統黑客松習慣問題導向（遇到什麼問題、解決什麼問題）；創新創業競賽則更看重是否滿足使用者的渴望。這場比賽名叫黑客松，實質上是創新創業競賽，所以對外說明（影片、README、提交文字）**兩個面向都要講**：問題說明為什麼現在非做不可，渴望說明使用者為什麼會想用、會留下來。

**為什麼是現在**：網路讓同一份內容送到所有人面前；AI 第一次讓「把每個人獨特的問題，對到專屬的解法」做得起來。軟體市場也需要這種一對一的配對：每個人的工作流程、系統、語言、預算、隱私要求都不同，最紅的那一款不一定適合你。

**現有平台補不到這一塊**：有名的軟體已經被整理得很好。G2、Capterra 這類評論站，Toolradar 這類已有 MCP 的工具目錄（上萬款工具），還有 ChatGPT 自己的 plugin 目錄，都以知名的商業 SaaS 為主，營收也多半來自廠商。**高品質、但默默無聞的長尾軟體**，沒有人在系統性地收。

**一個真實的例子（團隊成員的親身經驗）**：為了找一個好用的語音輸入工具，花了半個月比較各種替代品，最後是在 GitHub 動態牆上偶然點開朋友做的 App，才發現它就是要的：準確、即時，背後用的語音模型價格只有大廠的十分之一。但直接搜尋「最新語音辨識服務」，幾乎找不到它。**好東西早就存在，只是沒有一條路通到使用者這裡。**

## 2. 方向調整：從「繁中語音輸入」到「全球的寶藏軟體」

賽前的規劃把第一步鎖定在「台灣開發者的繁中桌面語音輸入」。為了這次 Meta 黑客松，這個範圍**太窄、太在地**，改成：

| | 賽前的規劃 | 黑客松的目標 |
|---|---|---|
| 使用者 | 台灣開發者，10–20 人 | 全球使用 AI agent 的人 |
| 軟體範圍 | 一個類別（語音輸入），手寫 15–40 筆 | 不限類別，重點是**默默無聞但品質好**的軟體 |
| 資料怎麼來 | 人工手寫、逐筆查證 | **agent 自動發現、讀懂、實際驗證**，人工抽查 |
| 核心價值 | 推得比 agent 自己查更準 | 找到 agent 自己找不到的，而且確認裝得起來、用得了 |

**保留不變的核心理念**：
- **我們是知識，不是手。** agent 負責執行指令、安裝、操作；我們負責告訴它該用哪個、怎麼裝、怎麼上手。打個比方：我們不做導航 App，我們做地圖資料。
- **推薦是配對，不是排名。** 沒有「最好的軟體」，只有「最適合你的」：作業系統、預算、隱私（能否本機執行）、語言、工作流程都不同。每一類軟體在意的東西也不同（例如手機記帳在意有沒有廣告，語音輸入在意準確度與隱私），所以每一類要有自己的「在意清單」。
- **中立。** 不屬於任何一家 agent 生態系，所以可以推薦大廠不會主動推薦的選項，包括「你不需要付費」與「內建的就夠了」。大廠有能力做推薦，但有利益衝突：它們的 agent 很難真心推薦對手或免費的本機工具。中立不是永久的優勢，只有一直守住規矩才成立。
- **看結果，不只看評論。** 最可信的訊號是「裝了沒、還在用嗎、換成什麼」，不是星數或五星評論。這些結果會隨使用累積，是平台長期的價值所在（見第 3.1 節）。
- **「推對」分三層。** 第一層是推對軟體，這只是門檻，通用 agent 常常也會碰巧推對。第二層是選對模型與設定，幾分鐘內裝好、設好，這是我們主要的戰場。第三層是該說「內建就夠了」的時候誠實說（例如公司電腦沒有管理員權限），信任從這裡來。

**優先服務的使用者**：不想讓工作流程綁在單一訂閱上的人、在意隱私與本機執行的人、預算有限的學生和小團隊、有特殊語言需求的人、同時用好幾家 agent 的人。這群人也最常自己做軟體、分享作品，和供給端高度重疊。

### 2.1 11/1 修訂：定位、GUI App 與來源整合

開賽時定的範圍是為了先把路做通。到 11/1，開發者 CLI、本地 AI、MCP server 三類已經能自動安裝、驗證、上線，所以念誠在 11/1 修訂下面幾點：

- **定位：人的軟體顧問，透過人的 agent 交付。** 來問 pickfit 的是使用者本人（產品網頁）或他的 agent（MCP）。被推薦的軟體可以是人自己用的（GUI App、CLI、本地 AI），也可以是給 agent 用的（MCP server）；兩種都收，但服務的對象始終是人。MCP server 是「替你的 agent 加上新能力」的一類，不是全部。
- **GUI App 納入範圍，深度要做到。** 受硬體與額度限制，數量可以少，但通過的每一款都要做到 function：在虛擬螢幕上啟動，Meta 模型看截圖決定點哪裡、輸入什麼，動作由 pickfit 執行，再用能檢查的結果（存出的檔案、剪貼簿、畫面上讀到的文字）確認功能真的有效。Linux（Xvfb）先做，macOS（tart，經 VNC）其次，Windows 看時間。做不到的照舊標「未驗證」，不假裝。
- **來源整合是核心價值。** 好軟體分散在各個平台，各有各的目錄，沒有人把它們整合起來並實際測過。除了 GitHub、Show HN 與投稿，11/1 起把 Flathub（Linux GUI）與 Homebrew Cask（macOS GUI）當成發現來源（不只算熱門度），winget（Windows）看時間；同一款軟體從不同來源進來，合併成一筆。每個來源先收少量，重點是整條路通：發現 → 抽取 → 在對應的作業系統上驗證 → 上線。
- **時程**：GUI 操作檢查與新來源的凍結延到 11/3 12:00；其他照舊在 11/2 晚上凍結。

## 3. 願景

> **好軟體靠實力被找到，也養得活做它的人。**

如果「發現」這件事被解決，軟體的競爭方式就會改變：贏的不再是行銷預算最多的，而是最用心、最替使用者著想的。對獨立開發者來說，這是第一次不必會行銷，作品也能被需要的人找到。

**更大的圖像：讓世界共享已經做出來的成果。** 每天都有人做出好軟體，也每天都有人在重做一樣的東西。pickfit 要讓已經存在的好軟體被真正用到，把它們的價值放到最大；也讓做軟體的人知道彼此在做什麼，少一點重複，多一點在別人的成果上往前走。使用者不必自己從頭做、自己維護、自己付 token；開發者的作品找得到用的人。

本節的理念來自賽前的構想討論；這裡只記概念，程式、資料與評測都在比賽期間製作。

### 3.1 平台長期的價值：真實使用結果會累積

**一開始沒有使用者，所以不靠評論。** 長尾軟體本來就幾乎沒有評論。第一批資料靠主動發現、公開的維護與下載資料，以及沙盒實際驗證來建立。這是冷啟動的做法，不是平台的終點。

**平台上線後，每一次真實使用都會留下紀錄。** 使用者本人或他的 AI agent 透過 MCP 查詢、安裝、回報，平台就累積下「這款軟體對誰、在什麼環境下，實際用起來怎樣」。很多紀錄不需要任何人主動寫評論：

| 紀錄 | 從哪裡來 | 可信度 |
|---|---|---|
| 需求與條件 | 查詢本身就帶著 | 高，每次都有 |
| 選了哪一款 | agent 拿安裝指南時一定會來 | 高 |
| 裝好了沒、第一次執行成功沒 | `report_outcome` | 高 |
| 換掉了、換成什麼、為什麼 | 回來找替代品時一定會說（`find_alternatives` 要求帶上目前用什麼、哪裡不滿意） | 高，但只有負面 |
| 還在用嗎 | `report_outcome` 的後續回報，由 agent 在使用者同意後做一次 check-in（見下方）；長期可由本機盤點工具補上（見 3.2） | 最高 |
| 主動心得 | 使用者或 agent 自願留下的一段話 | 最低，量也最少 |

**這些紀錄回到平台，讓下一個人得到更好的答案。**
- 失敗回報會觸發重新驗證，修正後的安裝步驟寫回資料。
- 成功率、留存率進入品質分數。資料少的時候以驗證與公開資料為主；同一款軟體累積到足夠的外部回報之後，使用結果的權重逐步提高。
- 比較每款軟體「被換掉的比例」，抱怨的多寡就不會失真。

**黑客松期間怎麼量「還在用嗎」：agent 做的 check-in，沒有常駐程式。**
- **量什麼。** `get_install_guide` 的回應帶 `check_in`：裝好一週後、120 天內，使用者下次跟 agent 談到軟體或自己問起時，agent 先問「可以檢查一下你還在用 X 嗎？」，同意了才在本機跑幾個唯讀指令（`command -v`、套件管理器只列這一個工具、MCP client 的設定、macOS app 的 `kMDItemLastUsedDate`），再用 `report_outcome` 回報 `still_using`、`replaced` 或 `abandoned`，加上粗略的 `last_used`（這週、這個月、更早、不知道）。這些後續回報只要帶 120 天內發的 `rec_id` 就計分（安裝與第一次執行仍是 7 天）。指令由程式從錄下的安裝步驟產生，不經過模型。
- **永遠不收什麼。** 指令的輸出、確切的使用時間、路徑、這台電腦上的其他軟體、IP、使用者原話都不送出；`last_used` 在 D1 只收四個值，確切時間存不進去。只檢查 pickfit 推薦給這位使用者、agent 手上有 `rec_id` 的工具。使用者說不，就什麼都不回報。
- **為什麼黑客松期間不做常駐程式。** 常駐的盤點工具要使用者另外安裝、長期在背景執行、看得到整台電腦，信任門檻高，也需要簽章、更新與移除流程，九天內做不到能讓人放心的程度（第 9 節）。check-in 每次都是使用者看得到、可以拒絕的一次對話，量到的是同一件事，只是頻率低、量也少。計分仍照原規則：外部回報不到 3 筆時，使用結果（含留存）不占權重。
- **想自己檢查的人。** `scripts/checkin.py` 是一次性的開源腳本（只用 Python 標準函式庫），使用者自己跑、或自己排程：只檢查 pickfit 推薦過、使用者留著 `rec_id` 的工具，只跑 pickfit 寫的那幾種唯讀指令（其他一律跳過），先印出要送的內容，打 yes 才送。這是 3.2 本機盤點工具的小原型，用來 demo；pickfit 不幫使用者裝任何東西。

**為什麼這是核心價值。** MCP 協定和軟體目錄，誰都做得出來。難以複製的是兩樣東西：跨所有 agent 匯集的真實使用結果，以及中立的信譽。單一家 agent 只看得到自己的使用者，我們看得到全部。越多人用，推薦越準，越多人用，平台因此能長期維持下去。

**黑客松期間能證明到哪裡。** 能 demo 的是閉環本身：回報 → 重驗 → 安裝步驟被修正。樣本太少，還不能宣稱「資料越多推薦越準」；這兩件事要分開說。評測與 demo 產生的回報另外標示，不算進分數。

### 3.2 長期會長出來的東西（黑客松不做）

- **完整的網頁版**（黑客松期間先做自然語言搜尋的產品網頁，見第 4.5 節）：給還沒用 agent 的人；也讓開發者看到自己的作品被誰找到、裝起來的情況。透過 agent 使用時，使用者通常不知道背後是誰推薦的，網頁版是品牌唯一會被直接看見的地方。
- **本機盤點工具**：不是 agent，只在使用者同意後，匿名回報這台電腦裝了什麼、多久用一次。agent 通常只在使用者不滿意時才回來，盤點工具補上「用得好好的」那一半，留存資料因此最可信。
- **需求地圖**：大家在找、卻找不到好軟體的需求，是給獨立開發者的訊號：下一個值得做的東西是什麼。這把「發現」接回願景的另一半。

### 3.3 收錄的兩條路：主動發現，加上開發者投稿

**黑客松期間以主動發現為主。** 我們主動從公開來源收集軟體、讀懂、驗證、計分，再收進資料庫。這是冷啟動的做法，也是長期的其中一條路，但不會是全部。

**長期有很大一部分會來自開發者主動投稿。** 主動發現只找得到「在公開來源留下足夠訊號」的軟體。很多真正創新的作品，或替小眾市場量身做的應用程式，作者不在 GitHub 熱門榜上，也沒在宣傳；讓作者自己送進來，才收得到這些。供給越多元，越能對上使用者方方面面的需求：特定的工作流程、語言、產業、裝置與預算。

**兩條路用同一套 agentic 審查。** 我們現在為主動發現做的流程（讀懂 → 沙盒實際安裝驗證 → 計分），就是將來審查投稿作品的流程：作者送出連結，agent 讀懂、裝起來試、判讀畫面、算出寶藏分數，通過的才進資料庫。審查標準對兩條路一樣，投稿不會因為是作者自己送的就被放寬或加分，這是中立的一部分（見第 2 節）。第 4.1 節的提交入口，就是這條路在黑客松期間的最小版本。

**投稿的人也得到回饋。** 沒通過時，作者拿到具體原因（例如照 README 裝不起來、卡在哪一步），可以修好再送；這對小專案本身就有價值。

## 4. 黑客松要交出的東西

八天內做出一條能 demo 的完整路徑：**發現 → 讀懂 → 驗證 → 配對 → 安裝 → 回報**。

### 4.1 發現 agent（Discovery）

從公開來源收集「可能是好軟體」的訊號，交給 Meta 模型判斷與整理。

- **來源**（授權規則見第 8 節）：GitHub（新建的 repo、topic、release、awesome 清單）、Hacker News 的 Show HN（官方 API）、Homebrew（含 Cask）、Flathub 與 winget 的套件資料（11/1 起當成發現來源，見第 2.1 節），以及 Threads、Facebook 上的分享（只走官方 API 或使用者提交的連結，**不爬網頁**）。
- **Meta 模型做的事**：讀 README、貼文、截圖，判斷「這是不是一個可以拿來用的軟體」，並抽出結構化的檔案：做什麼、適合誰、平台、安裝方式、價格模式、是否本機執行、授權、最近更新。
- **提交入口**：任何人（包括作者本人）貼一個 GitHub 或 Threads 連結，幾分鐘內就變成可被推薦的軟體。這同時是供給端的成長方式，也符合「在社群分享作品」的習慣。

### 4.2 驗證 agent（Verification）——我們和別人最大的差別

**不只看描述，實際裝起來試。** 在沙盒環境裡照 README 安裝並執行，記錄：
- 裝不裝得起來、要幾步、卡在哪裡；
- 實際可行的安裝與設定步驟（這是 agent 自己最容易答錯、也最有價值的資訊）；
- 執行畫面的截圖，交給 Meta 的視覺模型判斷是否真的能運作；
- GUI App 由 Meta 模型看截圖操作，再用能檢查的結果確認功能有效（第 2.1 節）。

驗證結果決定這款軟體能不能被推薦，也成為品質分數的一部分。

### 4.3 「寶藏分數」：品質與知名度分開算

- **品質**：驗證通過、文件完整度、維護是否活躍（最近 release、issue 回應）、真實使用者的提及與使用結果。使用結果的權重會隨外部回報累積而提高（見第 3.1 節）。
- **知名度**：星數、下載量、被搜尋到的難易度。
- **我們要找的是品質高、知名度低的那一群**，並在推薦時說明理由，不讓星數主導。

### 4.4 配對 MCP

一個 MCP server，讓任何 agent（Claude Code、Codex、其他 harness）都能查詢。先收斂到 4 個工具：

| 工具 | 做什麼 |
|---|---|
| `find_software` | 依需求與條件（OS、預算、隱私、語言）回傳 2–3 個最適合的選項，附理由與最好的免費選項 |
| `find_alternatives` | 找某個軟體的替代品；要求帶上「目前用什麼、哪裡不滿意」 |
| `get_install_guide` | 回傳在使用者系統上**經過驗證**的安裝與設定步驟，以及需要使用者手動完成的部分（例如權限授權） |
| `report_outcome` | agent 回報裝了沒、第一次執行成功了沒、還在用嗎、換成什麼、使用者是否滿意；可附一段簡短心得（選填） |

agent 最多先問一兩個最能分辨選項的問題，其餘交給使用回饋。`find_alternatives` 要求帶上「目前用什麼、哪裡不滿意」，因為不給就推薦不準；agent 為了幫使用者拿到更好的答案，自然會交出回饋。不需登入；回應裡不放推薦碼或廣告。

### 4.5 產品網頁（交件前必做，10/29 從「可選的展示頁」改成必做）

作品不能只有 MCP。MCP 仍是重點，讓每個人的 agent 都能用；但評審和一般人需要一個**看得到、馬上能試**的東西。

- **自然語言搜尋**：使用者在網頁上用一句話描述需求，背後用的就是同一套平台（同一份資料、同一套配對與 Meta 模型），回傳平台收錄中最適合他的軟體，附理由、驗證結果與安裝方式。網頁和 MCP 是同一個大腦的兩個入口，不另做一套。
- **品牌與品味**：pickfit 的設計、語氣與品味，透過這個實際的產品呈現出來。透過 agent 使用時品牌藏在背後（見第 3.2、13 節），網頁是品牌被直接看見的地方。
- **demo 的用法**：影片裡先用 AI agent 走完 MCP 的流程，再快速帶到網頁現場，讓評審親眼看到同一套平台的推薦。網頁也是最直接、評審自己能點開來試的 demo。
- 原本規劃的內容可以放進來：最近發現並驗證過的寶藏軟體、每筆「為什麼值得用」、讓開發者看到自己的作品被收錄。
- 帳號、金流仍不做（第 9 節）。

## 5. Demo 要錄下的那一刻

1. **使用者在自己的 agent 裡說**：「我想要一個 Mac 上、免費、能離線的 X 工具。」X 從第 14 節的兩個類別（開發者 CLI 工具、本地 AI／LLM 工具）裡，挑寶藏軟體確實比知名產品好的情境。
2. **對照**：同一個 agent 自己上網查，推薦的是知名但不合條件的產品，或今年才出現的好專案它根本不知道。
3. **接上我們的 MCP 後**：agent 推薦一個今年才出現、星數不多、但我們驗證過裝得起來而且好用的專案，說明理由，並附最好的免費選項。
4. **agent 照驗證過的步驟幫使用者裝好**，第一次執行就成功，並回報結果。
5. **回報讓平台變好**：一筆真實的失敗回報觸發重新驗證，安裝步驟被修正，下一個人照新步驟就裝得起來。
6. **供給端**：作者在 Threads 分享新作品，貼上連結後幾分鐘，它就被讀懂、驗證，出現在推薦結果裡。
7. **產品網頁**：從 agent 快速帶到網頁現場，用一句自然語言搜尋，同一套平台給出推薦（第 4.5 節）。也可以放在第 3 幕後面，錄之前再排。

影片開頭第一句要說明賽前有什麼、這週做了什麼（官方要求，見 [hackathon-rules.md](hackathon-rules.md) 第 7 節）。

### 5.1 影片要講清楚的：問題與長期規劃

影片只有 3 分鐘，大部分要留給上面的實際操作；但開頭與結尾要讓評審清楚知道**我們要解決多大的問題、完整的長期規劃是什麼**，不然 demo 看起來只是一個推薦工具。篇幅短，但不能省。

**問題與渴望（開頭，約 20–25 秒）**：兩個面向都講（理由見第 1 節最後一段）。
- 問題：軟體分散在各個地方，大家都在做自己的軟體。但很多很棒、甚至更符合需求的軟體早就存在，只是找不到；agent 也不認識。自己做有代價：要維護、要成本，現在還多了 AI 的 token 費用。
- 渴望：用一句第一人稱的話帶出來，例如「我想要的，是一個 AI 幫我找到合適的軟體，而不是什麼都自己做」。接下來的 demo 就是在實現這句話。
- 順序可以先渴望後問題（先讓評審有共鳴，再說為什麼現在做不到），或反過來；錄之前兩種都試講一次再決定。

**長期規劃（結尾，約 20–30 秒）**：
- 黑客松期間我們主動發現、審查軟體；長期還會有很多開發者主動投稿，收進創新、小眾、客製化的作品，對上使用者方方面面的需求。
- 投稿用的就是影片裡這套 agentic 審查：讀懂、實際裝起來驗證、計分（第 3.3 節）。
- 每次真實使用都會回到平台，讓推薦越來越準（第 3.1 節）。
- 願景一句話收尾：讓已經存在的好軟體被用到、價值最大化，讓世界上的人共享彼此的成果，知道對方在做什麼。

講長期規劃時要清楚標示哪些是**這週做出來的**、哪些是**之後的規劃**，不要讓評審以為還沒做的已經做好了。

## 6. Meta 模型怎麼用（評分 25%，第一輪必查）

Meta 的模型必須是產品實際運作的核心，不是外掛。開工前先查官方文件確認各模型的實際能力與名稱。

| 環節 | 模型 | 用途 |
|---|---|---|
| 讀懂與抽取 | Muse Spark（Meta Model API） | 讀 README、貼文、release notes，判斷是不是可用的軟體，抽出結構化檔案 |
| 驗證判讀 | Muse Spark 的多模態能力 | 看執行截圖，判斷軟體是否真的在運作；讀安裝錯誤訊息並嘗試修正 |
| 大量初篩 | Muse Spark Open 或 Muse Glimmer（開放權重，透過 Baseten 或 Modal） | 便宜地大量過濾候選 repo 與貼文；同時爭取「Best Build on Meta Open Weight Models」 |
| 配對 | Muse Spark | 把使用者的自然語言需求對到條件與候選，產生推薦理由 |
| （選用）影音 | Muse Voice Transcribe | 有些作者用影片介紹作品，轉成文字後一起讀 |

可以同時用非 Meta 的工具，但要讓評審一眼看出 Meta 模型在哪裡、做了什麼。README 要有一節專門說明。

## 11. 建議的技術方向

接手的人可以調整，但改之前先想清楚理由。

- **MCP server**：無狀態，部署在 Cloudflare Worker 這類 serverless 環境，團隊熟悉、成本低。後端不一定要部署才能交件，但 demo 要能真的連上。
- **資料**：每款軟體一份 YAML（或 JSON），放在 git 裡當正本；事件記錄（查詢、回報）用一張簡單的表，不記 IP。
- **發現與驗證管線**：Python 腳本或 worker；沙盒可考慮 Modal 的 sandbox（合作夥伴有 credits）。
- **檔案欄位**：`slug`（永不改）、`name`、`summary`、`homepage`、`repo`、`platforms`、`install`、`pricing`、`open_source`、`license`、`processing`（local／cloud／hybrid）、`last_release`、`verification`（結果、步驟、截圖、時間）、`scores`（品質、知名度）、`sources`。
- **金鑰**：一律放 `.env`，不要 commit。

## 13. 風險

- **範圍太大**：「全球、不限類別」做不完，而且是一個人做。demo 只做兩個類別（見第 14 節），把整條路徑做深，比 20 個類別都做淺好。時間不夠時，依序砍：Threads 提交入口 → 開放權重初篩。產品網頁不砍（第 4.5 節），但可以縮成只有搜尋與結果頁。
- **驗證很難自動化**：GUI 軟體、需要權限的軟體、只支援特定 OS 的軟體很難在沙盒裡跑。先從 CLI 與網頁工具做起，其餘標成「未驗證」，不要假裝驗證過。11/1 修訂：GUI App 納入，少量但要做到 function（第 2.1 節）；做不到的仍標未驗證。
- **品質判斷會被灌水**：開放提交一定有人刷。黑客松期間由驗證結果與人工抽查把關，並在 README 誠實說明。
- **已經有人在做目錄與 MCP**：差別要放在「找得到長尾」、「實際驗證」與「累積真實使用結果」，不是「有 MCP」。只有 MCP 不夠，資料的深度與品質才是差別。大廠也開始在自己的生態系裡推薦軟體，但不會推薦對手或免費的本機工具。
- **使用結果累積得慢**：選軟體多半是低頻決定，選好就很少換；回報也可能被灌水或操縱。只計外部回報、需要足夠筆數才計分，並在 README 說明目前的資料量。
- **品牌藏在 agent 後面**：使用者可能不知道是誰推薦的。回應裡附 `how_we_know`，說明推薦依據。
- **被看成基本 RAG**：見第 7 節。

**為什麼選這兩個類別**：

- **本地 AI／LLM 工具**（本地模型執行器、推論伺服器、離線 AI 小工具等）：今年的新專案很多，模型的訓練資料多半不認識；也呼應 Meta 開放權重模型的主題。
- **語音輸入**等 GUI 軟體需要麥克風、輔助使用等權限，沙盒很難自動驗證，黑客松期間不當 demo 主軸；資料可以收，但標成「未驗證」。11/1 修訂：GUI App 納入範圍，見第 2.1 節。
