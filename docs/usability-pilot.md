# 易用性（ease.v1）試點：抽樣規則與通過標準

依據 [usability-proposal.md](usability-proposal.md) 第 5 節。念誠 11/2 同意第 9 節四點，並要求先試跑 12 款。

## 1. 抽哪 12 款

規則寫在 `scripts/ease_pilot.py`，結果在 `data/calibration/ease-pilot.json`。只讀 `data/software` 的紀錄和 `~/.pickfit/evidence` 的 run 資料夾，不看任何模型評分。

- 種子：`pickfit-ease.v1-pilot-2026-11-02`。每一層把 App 照 `sha256("<種子>:<slug>")` 由小到大排，取最前面的；各層依序抽，抽過的不再抽。
- 已有影片的 GUI 4 款（提案點名）：concessio、nip4、breaktimer-app、neon-vision-editor。
- 「好看但難用」探針 2 款：GUI 的某個 run 畫面是 main_ui、有一個操作通過 pickfit 的檢查，而且同一個 run 的 report.json 裡有操作卡到步數上限（step_cap）或放棄（give_up）。要求「有通過的操作」，是為了讓「使用中」那次呼叫有東西可看；不然探針只會測到第一眼（池子 13 款）。
- 只啟動過的 GUI：Linux 1 款、macOS 1 款（所有 GUI run 都沒有通過的操作）。
- 操作過的網頁 3 款（有 function 等級的 run）、只到 install 的網頁 1 款。

抽到的 12 款：concessio、nip4、breaktimer-app、neon-vision-editor；探針 portfolio、usdx；只啟動 pinit（Linux）、eli-v2-0（macOS）；網頁 capitolisation、farsimatrix、orrery；只到 install 的網頁 stock-fundamental-analysis-tool。

## 2. 提案沒寫死、這次先定下來的地方

- **兩次取樣怎麼合**：每個維度兩次都要有分，取平均；兩次差兩級（0 和 2）記「評審不一致」，不給分。任一次沒分（引用找不到、沙盒弄壞、沒歸因到 app）也不給分。
- **只看了第一眼**（run 裡沒有通過的操作）：易用性 = 第一眼兩個維度的加權分 × 0.6，和沙盒驗證「只啟動 0.6」同樣是乘數，所以最高 60。頁面不顯示總分。
- **判語**：pickfit 易用性 ≥70「容易上手」、40–69「有些卡關」、<40「不好上手」。念誠的整體 1–5：4–5 容易上手、3 有些卡關、1–2 不好上手。只看了第一眼的 App 不給判語。
- **扣分要歸因到 app**：低於 2 分的維度要有一條歸因為 app 的發現，並引用 OCR／DOM 找得到的字；只歸因到操作員或環境的，該維度不給分（不是 2，也不是 0）。

## 3. 通過標準（四條都要過）

1. **每個維度的一致度**：只算 pickfit 和念誠都有給 0/1/2 的 App（任一邊「看不出來」或沒分就不算）。差距 ≤1 級的比例要 ≥ 10/12（約 83%），而且每個維度至少有 5 款可比。
2. **整體排序**：念誠的整體分數（1–5）和 pickfit 易用性（0–100）的 Spearman ≥ 0.5，只算 pickfit 有易用性分數的 App。
3. **探針**：兩個探針的易用性都 ≤ 50。
4. **判語**：沒有任何一款差到兩個判語等級（一邊「容易上手」、一邊「不好上手」）；只算雙方都有判語的 App。

同時回報、但不算進通過標準：1.3 自己兩次的一致度、Muse Spark Open（Modal）的交叉一致度（有時間才跑）、易用性和知名度的 Spearman（|rho| 應 ≤ 0.3）、同一款 App 在 Linux 和 macOS 的分差（這次的 12 款如果沒有雙平台的就寫沒有）。

## 4. 沒過怎麼辦

- 只能改一次評分標準或 prompt，不能加分數偏移；改完同樣這 12 款重跑，用同一份念誠的評分比對。
- 還是不過：易用性改成只顯示、不計分，也不進寶藏門檻。

## 5. 念誠評分時看不到的東西

盲評頁（`scripts/ease_sheet.py` 產生）只放模型看到的同一批畫面、操作目標和同一份評分標準，不放 pickfit 的分數、發現或判語。評分存在 `data/calibration/ease-ratings.yaml`（不在 eval/）。pickfit 的分數在念誠存檔之後才比對。

## 7. 探索性對照：是模型還是 prompt（11/3，付費呼叫前 commit）

**這是事先規則（只允許改一次）之後的探索，不推翻第 6 節「沒過」的判定**，也不改紀錄、`EASE_SCORED` 或 worker。念誠想知道落差來自評審模型，還是來自「不評風格」這條指令。

**設計**：2×2，同樣 12 款、同樣證據（`bundle_for`）、同樣 OCR／DOM 引用檢查、每格每款取樣 2 次，比對念誠同一份評分（`8a6ff111`）。程式在 `scripts/ease_contrast.py`。

| | P1：r1 現行 prompt（`0193989a`，不評風格） | P2：也評視覺設計 |
|---|---|---|
| muse-spark-1.3 | muse-p1：第 6 節 r1 重跑的結果，直接沿用 | muse-p2 |
| claude-opus-5-5（只當對照） | opus-p1 | opus-p2 |

- **P2 只改第一眼的「看起來舒服」**：拿掉「Do not judge colours, style or branding」，改成也看新舊與精緻度、間距與對齊、破圖、視覺層次。檢核從 5 項變 6 項：字好讀、版面完整、間距與對齊、視覺層次、看起來新且完成度高、沒有東西蓋住。換算規則不變（沒有 app 的問題 2、一項 1、兩項以上 0）。仍然要引用畫面上的字、只扣 app 造成的問題、看不出來就給 null；「使用中」那次呼叫和 P1 完全一樣。
- **Opus 的設定**：Messages API、同樣的圖和文字、同樣的 strict JSON schema（`output_config.format`），effort 固定 `low`（和 muse-spark-1.3 的 reasoning effort 一樣），不送 temperature，不開 refusal fallback（確保每個答案都是 claude-opus-5-5 的）。專案規則不准計分的 session 讀 `eval/`，所以沒有參考 `eval/runner/config.json`。每次呼叫的 token 和花費記在結果檔和共用帳本（budget `anthropic-research`）。
- **花費上限**：Anthropic $15（帳本強制）、Meta $2（scope 上限）。先用 1 款試算，估計會超過就停。

**每格要報的數字**：`scripts/ease_compare.py` 的四個標準和是否全過；和念誠整體分的 Spearman；「看起來舒服」差距 ≤1 級的比例；探針 portfolio、usdx 的分數；兩次取樣的一致度；花費。

**怎麼下結論（事先定）**：
- 模型效果 = 兩種 prompt 下（Opus − Muse）的 Spearman 差，取平均。
- prompt 效果 = 兩種模型下（P2 − P1）的 Spearman 差，取平均。
- 某個效果 ≥ 0.3，而且兩組裡方向一致，才算「有影響」。
- 結論：只有模型有影響就是「模型的問題」，只有 prompt 就是「prompt 的問題」，兩個都有就是「兩者都有」，都沒有就是「都不是，或 12 款看不出來」。也會寫是否有任何一格四條全過。

**限制（不論結果都會寫）**：
- 只有 12 款（Spearman 只有 9 款可比），由一位評分者評，數字雜訊大。
- P2 是看過念誠的評分之後才寫的；任何一格「看起來過了」，都是用同樣 12 款調出來的，有過度擬合的風險。
- 要上線，得用一組念誠沒評過的新 App 另外驗證，而且產品裡的評審必須是 Meta 模型；Opus 只能當對照。

- 模型效果：Opus 減 Muse 的 Spearman 差，P1 是 +0.58、P2 是 +0.56，平均 +0.57，方向一致，**算有影響**。
- prompt 效果：P2 減 P1 的差，Muse 是 +0.03、Opus 是 0.00，平均 +0.01，**不算有影響**。
- 結論是「模型的問題」，但**四格都沒過**。

看得到的細節：
- Opus 的「看起來舒服」和念誠比較接近：P2 下給 neon-vision-editor 0 分，和念誠一樣；farsimatrix、orrery 也有扣分。

- Opus 的解碼沒有受 schema 約束，這是和 Muse 不同的一點。
