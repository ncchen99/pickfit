**Main recommendation:** Don't try to teach a tiny model the textbooks. Use a hybrid: a small instruction model on the phone, plus a local search over your content (RAG), plus a plain question bank. Do most of the hard work ahead of time on a computer with a big model, and ship the results as static data. Leave fine-tuning for later, and use it only to shape tone and format.

**My assumptions:** mid-range Android phones with 4–6 GB of RAM, English content, and at least one subject that involves math. If you need iOS, or very low-end phones, the choices below change a little, and I note where.

## 1. Which model

| Phone RAM | Model to try first | Approx. size (4-bit) |
|---|---|---|
| 3–4 GB | Qwen3 1.7B or Gemma 3 1B (Qwen3 0.6B as a fallback) | ~0.5–1.1 GB |
| 6 GB+ | Gemma 4 E2B / Gemma 3n E2B, or Qwen3 4B | ~1.5–2.5 GB |

- Test 2–3 of these on your real questions before you pick one. Rankings shift every few months, and some of the newer claims (for example about Gemma 4) come from secondary sources.
- **Licenses:** Qwen uses Apache 2.0, which is simple. Gemma has its own terms of use, so read them before you distribute the app.
- If you use Qwen3, turn off its "thinking" mode (`/no_think`). Otherwise it's slow on a phone.
- **Embedding model** (turns text into vectors for search): EmbeddingGemma-300M, or something smaller like bge-small or MiniLM. Also add plain keyword search with SQLite FTS5. Exact syllabus terms like "photosynthesis" or "quadratic formula" match very well with keywords.

## 2. Architecture: RAG plus a question bank, not a purely generative model

A 1–4B model cannot reliably memorize three textbooks. Fine-tuning facts into it produces confident wrong answers. RAG keeps answers tied to the books and within the syllabus.

**Before release, on a PC or in the cloud:**
1. **Extract** the textbooks and papers to text. Equations, tables and diagrams are the painful part, so budget time to check them by hand.
2. **Chunk** the books by section (about 200–400 words each). Tag every chunk with subject → syllabus topic → subtopic.
3. **Build a question bank.** Store each past or practice question with its marked answer, year, marks and topic tags. This needs no LLM at runtime: "practice topic X" becomes a database query. That's the most reliable feature you'll have.
4. **Use a large model to pre-generate content,** for example:
   - worked explanations for each topic and for past questions
   - common mistakes
   - "similar question" variants
5. **Have a teacher review that content,** then ship it. A big model with human review beats a tiny model working live on the phone.
6. **Bundle it all** as one SQLite file containing text, tags, embeddings (via sqlite-vec) and the FTS index.

**At runtime, on the phone:**
- **Student asks a question:**
  1. Detect the subject and topic.
  2. Run keyword and vector search, limited to that subject.
  3. Pass the top 3–5 chunks to the model with a prompt like: "Explain at high-school level using ONLY these excerpts; if not covered, say so and point to the chapter."
  4. Show the source (book, chapter, page) under the answer.
- **Practice mode:**
  1. Fetch real questions by topic first.
  2. "Generate similar" serves the pre-reviewed variants. Live generation should be clearly labeled "AI-generated, unverified."
  3. For math-like questions, use templates with random numbers, where code computes the answer. Don't let the LLM do the arithmetic.
- **Marking:** compare the student's answer with the stored mark scheme. You can let the model give hints, but the official answer must be shown alongside them.

## 3. Training (later, optional)
Once RAG works, you can fine-tune with LoRA (Unsloth on Colab is the easiest route for beginners). Train on a few thousand examples of "question + retrieved excerpts → good tutor-style answer," generated by a big model and checked by people. This improves:
- tone and format
- willingness to say "this isn't in your syllabus"

It doesn't add knowledge. Then export to GGUF (for llama.cpp) or `.task`/LiteRT (for MediaPipe).

## 4. Install and first-run steps (prototype on a laptop first)
1. **Install Ollama** from ollama.com, then:
   ```
   ollama pull qwen3:1.7b
   ollama pull gemma3:1b
   ollama pull embeddinggemma
   ollama run qwen3:1.7b "/no_think Explain osmosis for a 15-year-old in 5 sentences."
   ```
2. **Set up Python:**
   ```
   python -m venv venv && source venv/bin/activate
   pip install pymupdf sqlite-vec ollama
   ```
   Write a small script that:
   - extracts one chapter
   - chunks it and embeds the chunks
   - stores them in SQLite
   - retrieves the top chunks for a question and prompts the model
3. **Build a test set** of 50 real student-style questions per subject with expected answers. Compare the models on it.
4. **Try the model on a real phone** before writing any app code. Google AI Edge Gallery or PocketPal AI (llama.cpp-based) will do. Check speed, heat and RAM use.
5. **Build the app:**
   - Android: Flutter + `flutter_gemma` / `ai_edge_rag` (MediaPipe; the RAG part is Android-only for now).
   - Android and iOS: React Native + llama.cpp bindings (`llama.rn` / `@react-native-ai/llama`) + sqlite-vec.

## 5. Challenges and workarounds
- **Hallucination:** use retrieval only, show citations, let the model say "not in syllabus," and rely on pre-reviewed content.
- **Weak math and reasoning in small models:** use the books' worked solutions, pre-generated steps, and template questions where code computes the answer. Never trust the tiny model's arithmetic.
- **PDF extraction** (formulas, diagrams): fix it by hand, store formulas as LaTeX, and show diagram images instead of describing them.
- **App size** (1–3 GB): download the model once over Wi‑Fi on first launch. Offer a smaller model for low-end phones.
- **Speed, battery and heat:** keep prompts short (only 3–5 chunks), cap answer length, and stream the output.
- **Topic drift and misuse:** a topic classifier plus a system prompt, and refuse anything off-syllabus. Students are minors, so add basic safety filtering.
- **Copyright:** check that you have the rights to put the textbook and exam text inside an app.
- **Evaluation:** have teachers grade the outputs on your fixed test set every time you change the model, prompt or data.

Phases: (1) the question bank alone, with no LLM, which is already useful; (2) RAG explanations; (3) fine-tuning, only if the tone or format still needs work.
