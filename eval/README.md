# 評測：題組與評分方式

題目在 [questions.yaml](questions.yaml)。這份說明和題目在**同一個 commit** 凍結，凍結時間就是那個 commit 的時間。

## 1. 這份評測要回答什麼

同一個 AI agent，**接上 pickfit 之後**，推薦的軟體是不是比它自己上網查**更符合使用者的條件、裝得起來、第一次執行就成功**；在該說「內建的就夠了」的時候，有沒有誠實說。

## 2. 題目怎麼來的

- 2026-10-28（比賽期間）新寫，沒有使用賽前的評測草稿。
- 由 AI agent 起草：3 個 agent 各從一個角度起草（使用者情境、知名工具不符條件的情況、誠實與涵蓋度），共 42 題；1 個 agent 挑出 20 題；3 個 agent 分別從公平性、可量測性、真實性審查；最後 1 個 agent 依審查修改定稿。念誠逐題審定後凍結。
- 題目只寫需求與可檢查的條件，**不寫預期答案**。
- 組成：開發者 CLI 工具 10 題、本地 AI／LLM 工具 10 題；找軟體 14 題、找替代品 4 題、「內建就夠」2 題；繁體中文 5 題；可在 Linux 容器驗證 17 題、只能在 Mac 驗證 3 題（q08、q11、q12）。

## 3. 凍結與防止照題目準備資料

- 凍結後**不改題目與檢查項目**。唯一允許的修改是「對任何答案都壞掉」的測試資料或檢查腳本：要在任何一組開跑前 commit 並寫明原因，兩組一起套用。勘誤寫在本文第 9 節。
- **建資料的 session**（發現、抽取、驗證、計分）**不讀 `eval/`**；只有評測執行與評分讀。讀過題目的 session 不寫 discovery 的 query。
- discovery 的 query 依類別寫，不從題目推導；每條 query 連同時間記在 trace。
- 檢查項目裡寫「at freeze」「pre-freeze」的測試資料、固定模型、版本，指的是**第一次開跑評測前 commit**（測試資料凍結）。題目與檢查項目本身在今天凍結。

## 4. 組別與執行方式

| 組別 | agent | 可用工具 |
|---|---|---|
| 對照組 | Claude Code 無頭模式 | WebSearch、WebFetch |
| 實驗組 | 同一版本 | WebSearch、WebFetch、pickfit MCP |
| rules-only（選做） | 同一版本 | 同實驗組，但 pickfit 關掉模型配對 |

- 三組用同一個 Claude Code 版本、模型、設定；版本記在結果裡。
- **隔離**：每題在空的暫存目錄執行，用 `--strict-mcp-config --mcp-config <檔案>`（對照組空的、實驗組只有 pickfit），不載入這台電腦使用者層級的其他 MCP（例如 toolradar）。不給 Bash、Edit、Write 等本機工具。
- 只送題目的 `prompt`，其他欄位只給評分者看。每題前面加同一段開場：`Recommend only; do not run commands or change files on this machine. If something is unclear, state your assumption and answer anyway. Put your main recommendation first and include install and first-run steps.`
- 單回合、不追問。**每題每組跑 1 次**（時間與預算限制；雜訊照實寫在結果裡）。各組在同一個 24 小時內跑完。pickfit 的程式與資料版本固定，記下 commit。
- 花費：先跑 2 題估單題花費；Anthropic 評測總花費上限 $30。

## 5. 評分

**評哪一個推薦**：第一個推薦，或答案明確標為首選的那個。若答案說另一個選項「一樣好」而它違反硬條件，L1 不過。

**三層檢查**（每個檢查項目都標了層級）：

| 層 | 意思 | 怎麼查 | 範圍 |
|---|---|---|---|
| L1 | 推對軟體：存在，且符合每個硬條件 | 查官方 repo、文件、授權 | **20 題全做** |
| L2 | 裝得起來、跑得動 | 照答案的步驟在乾淨環境實跑 | 先做「安裝＋第一次執行」，再做題目裡的進階檢查；兩組**依題號順序**做，做不完的兩組都標「未實跑」 |
| L3 | 該說「內建就夠了」時誠實說 | 讀答案 | q10、q20 |

- 「內建就夠」題：主要答案必須是內建做法，額外工具要標成選用，否則記 `unneeded_install`。
- 「找替代品」題：推薦繼續用現在的工具，只有每個檢查都過才算對。
- 答案寫了自訂腳本：題目允許寫程式時，只評 L2；題目排除寫程式時（q06），L1 不過。
- 答案說「沒有任何工具符合全部條件」：只有在全部跑完後，另開一個不接 pickfit 的 agent session 搜尋，念誠再自己搜尋 30 分鐘，都找不到通過 L1 的選項時，才算對。

**評分者可以做的調整**：填入版本號與佔位字、接受安裝程式預設值；Ubuntu 擋下裸 `pip install` 時改在 venv 裡跑（記 `needed_venv`，但「照步驟原樣成功」那一項不過）。**不可以**：修正錯的指令或旗標、補上缺的步驟、換掉答案指定的模型。

**執行環境**：
- Linux：Modal Sandbox（x86_64，和產品驗證同一套），image 以 `ubuntu:24.04` 為底，記下 image digest。安裝 20 分鐘、每個檢查 10 分鐘逾時。
- Mac（q08、q11、q12）：念誠的 Apple silicon Mac，用另開的 macOS 使用者帳號，每次跑完照清單移除裝過的東西。由念誠親手執行（`method: human`）。

**判讀模型輸出的檢查**（q11、q15、q16 等）：能固定 temperature 或 seed 就固定；不能就跑 3 次、2 次過算過。繁簡判斷用固定版本的 OpenCC（逐字判斷，繁體比例 ≥0.95 且至少 30 個繁簡不同字）。需要判斷語意時，用固定版本的 Claude 模型、固定評分說明，看不到組別。

**盲測偏好**：每題把兩組的答案去掉可辨識組別的字（pickfit、工具名換成 `[source]`），隨機排成 A／B；念誠在看到任何檢查結果前選 A、B 或平手，附一句理由。偏好和客觀結果並列，不覆蓋客觀結果。

**長尾標記**：推薦的工具 GitHub 星數 <1,000，或第一次公開發布在評分日前 18 個月內，就標長尾。只報告，不算輸贏。

## 6. 事先決定的難度分組

依「對照組自己找」的預期難度事先分組，避免事後挑題：

- 容易（不退步檢查）：q03、q04、q07、q08、q12、q13、q19、q20。實驗組在這組不應該比對照組差。
- 中等：q02、q05、q06、q09、q10、q14、q15、q17、q18。
- 困難：q01、q11、q16。
- **主要結果**：中等＋困難 12 題的通過率。20 題的完整結果一律並列。
- 相似題群（一筆資料可能同時影響幾題，報告時註明）：mcp-tooling（q01、q06）、local-openai-endpoint（q12、q13、q14、q20）、local-model-client（q18、q19）、traditional-chinese-output（q11、q15）。

## 7. 報告

README 列出每一題兩組的結果，**包括輸的題與兩組都沒過的題**；附逐字答案（原始與去識別版）、檢查紀錄、版本資訊。並寫明：

- 題目由 AI 起草、念誠審定並凍結；出題者與 pickfit 的開發者是同一個人（個人參賽）。
- 每題只跑 1 次。
- L2 實跑到第幾題、哪些題「未實跑」。
- q18、q19 是問某一家廠商的 agent，推薦跟該廠商無關的工具，所以也在測中立性。

## 8. 檢查項目裡的測試資料

各題 `success_checklist` 提到的測試資料（設定檔、log 產生器、CSV、PDF／DOCX、OpenAPI 規格、測試伺服器、音檔、文件夾等）在第一次開跑前 commit 到 `eval/fixtures/`。假的金鑰、token 在執行時產生，不 commit。q15 的音檔用 CC0 授權的公開中文錄音（念誠 2026-10-28 決定），附逐字稿與來源。

## 9. 勘誤

（凍結後若有修改，依第 3 節的規則記在這裡。）

### 9.1 開跑前追加的事先登記（2026-10-29）

這一節不是第 3 節所說的勘誤（第 3 節只允許修正壞掉的測試資料或檢查腳本），而是**開跑前追加的事先登記**。它不改題目、檢查項目與第 5 節的判準；第 1 次照第 4 節執行（每題每組 1 次），主要結果照第 6 節。

追加的原因：每題只跑 1 次時，雜訊可能決定輸贏；而且出題、開發、評分是同一個人。所以把重跑、門檻、評分程序、輸題原因，在看到任何答案前都寫定，減少事後選擇的空間。

本節在任何一組開跑前 commit，commit 時間就是登記時間。commit 後不再修改本節；之後的決定只能另寫小節（9.2、9.3…）追加，而且要在受影響的執行開始前 commit。念誠 2026-10-28 同意追加，2026-10-29 確認本節的數字（B4 的上限、A1 的 Meta 每日上限、C7 的 L2 截止時間、A5 要跑 rules-only）。

#### A. 開跑前固定的事

1. **評測專用部署**：開兩個部署，同一個程式 commit、同一份資料快照，都在開跑前建好：
   - `pickfit-eval`：模型配對，給實驗組；
   - `pickfit-eval-rules`：關掉模型配對，給 rules-only 組。

   兩個部署的共同規則：
   - 評測期間不切換設定，也不接評測以外的流量；
   - 只開放唯讀工具（找軟體、找替代品、安裝指南），不開放提交軟體、回報結果；
   - 找軟體的結果不快取；
   - Meta 每日上限 **$10**。
2. **評測期間不改 pickfit**：從第一題開跑，到所有組、所有次數跑完，這段期間：
   - 不改 pickfit 的程式、資料、提示詞與設定；
   - 不跑 `pickfit watch`、不 publish，也不處理回報或重驗。
3. **版本紀錄**：第一題開跑前與最後一次跑完後，各記一次：
   - pickfit 的 git commit 與兩個部署的版本 ID；
   - 資料快照、候選庫（`runs/pipeline.db`）、漏斗紀錄的 SHA-256；
   - Claude Code 版本與完整模型 ID。

   評測期間設 `DISABLE_AUTOUPDATER=1`。前後紀錄不同時，變動之後的所有執行作廢，用原快照依 B2 重跑，作廢紀錄一併報告。
4. **開跑前 commit 的腳本與提示**：D5 的比對腳本、C6「另開搜尋」用的固定提示、B2 的執行紀錄核對腳本。
5. **組別**：rules-only 組**要跑**，只跑第 1 次（G 允許砍除時例外）。

#### B. 執行

1. **第 1 次**：
   - 照題號順序跑。同一題各組接著跑，不同時並行。
   - 單號題對照組先跑，雙號題實驗組先跑；rules-only 排在最後。
   - q01、q02 就是第 4 節「先跑 2 題估花費」的那 2 題。它們算正式的第 1 次，不丟棄、不重跑（無效執行除外）。
2. **無效執行**：
   - 只有兩種情況算無效：Anthropic API 回錯誤（5xx、429、overloaded），或執行器本身當掉，以致沒有最終答案。
   - 無效時，立刻用相同設定重跑，最多 2 次，每次嘗試都保留並報告。3 次都無效，該題該次記「未跑」。
   - 下列情況都**不算**無效，照常評分：達到回合上限；逾時（評最後一則助理訊息）；答案空白、拒答或只反問；pickfit 回錯誤、逾時或標為降級（只用規則排序）。
   - 每次執行都是新的 `claude -p` 程序加新的空暫存目錄，不續接先前的對話；原始輸出用 `--output-format stream-json --verbose` 存檔。
   - 評分前，用腳本核對每次紀錄的 Claude Code 版本、模型與 MCP 工具清單。某組設定錯誤時，該組那一輪的 20 題全部作廢重跑，不能只重跑部分題。
3. **補充重跑**：
   - 所有組的第 1 次跑完後，對照組與實驗組每題再跑第 2、3 次，設定與第 1 次相同。
   - 照題號逐題跑，每題的順序是：對照 2、實驗 2、實驗 3、對照 3。
   - 只在兩種情況停止：時間到（照第 4 節，從 q01 第 1 次開跑起 24 小時），或花費到上限。不因其他原因提前停止。
   - 停止時正在跑的那一題，兩組都記「未跑」。報告寫明停止的時間、原因與花費。
4. **花費**：第 4 節的 $30 是花費的安全上限，不是檢查項目；Anthropic 額度原本就只給評測用。所以：
   - 第 1 次（三組）用第 4 節的 $30 上限；
   - 補充重跑另設上限 **$60**；
   - 評分用的 Claude 模型另設上限 **$20**（用於 C4、E 的第二評分者，以及第 5 節的語意判斷）。

   花費以 Claude Code 結果訊息的 `total_cost_usd` 與 API 用量累加。

   超出時：
   - q01、q02 跑完後，若預估第 1 次會超過 $30：在跑下一題之前另寫 9.2 定新上限，並 commit。
   - 補充重跑預估超過 $60：只跑第 2 次；仍超過，就照題號跑到上限為止。
   - 看到第 1 次的答案或分數之後，不追加任何預算。

#### C. 評分

1. **定義**：
   - 一題「L1 通過」＝該題所有 [L1] 項目都過。
   - q10、q20 沒有 [L1] 項目。本節凡說到 L1 的地方（C8、D1、D2、E），這兩題都改用該題的 [L3] 項目。
   - 一題「L2 通過」＝該題所有 [L2] 項目都實跑，而且都過。
   - 第 6 節的主要結果表把 L1、L2、L3 各層的通過題數分開列。D 的門檻只決定結論怎麼寫，不重新定義第 6 節。
2. **評哪一個答案**：
   - 照第 5 節，評首選。
   - 答案的主要結論是「沒有工具符合全部條件」時，照第 5 節評，即使後面附了「最接近的」工具。
   - 找不到可辨識的推薦時，L1 不過。
3. **要靠 L2 才能判 L1 的情況**：第 5 節有兩種，一是找替代品題推薦沿用現有工具，二是題目允許寫程式、答案給自訂腳本。
   - 第 1 次：以該題的 L2 結果判定。該題 L2 未實跑時，記 L1 不過並標出。
   - 補充重跑：記「無法判定」，不列入穩定性比較。
4. **盲評 L1**：
   - 從去識別的答案取出每個答案的首選（含指定的安裝方式）。
   - 把每題所有組、所有次數的首選去重、打亂順序，在不知道組別與次數的情況下逐一評 L1。同一題同一工具的判定，套用到所有推薦它的答案。
   - 只能從答案原文判斷的項目，用去識別的答案逐一評。
   - 固定版本的 Claude 模型用固定的評分說明，獨立評同一批（題、工具）。不一致的項目逐一列在報告；結果以念誠的判定為準。
5. **第 1 次先定案**：開始評補充重跑之前，先把第 1 次的評分 commit 到 `eval/results/`，包括 L1、L3，以及 L2 做到截止時的結果。之後不改；發現評錯，只能在勘誤區追加，原判與改判並列。
6. **「沒有工具符合」的查核**：
   - 每題只做一次，在所有執行結束後做，結果套用到該題所有組、所有次數。
   - 任何組、任何一次的答案推薦過且通過 L1 的工具，直接推翻「沒有工具符合」。
   - 另開的 agent session 用 A4 commit 的固定提示，不接 pickfit。
   - 念誠 30 分鐘搜尋時用的查詢與看過的連結全部記錄。
   - 查核時不看是哪一組說了「沒有工具符合」。
7. **L2**：
   - 只做對照組與實驗組第 1 次的答案。每個答案不論 L1 過不過都實跑。rules-only 只評 L1、L3。
   - Linux 題與 Mac 題（q08、q11、q12）各自依題號順序做，不跳題。
   - 截止時間是 **2026-11-03 12:00（台北）**。截止時正在做的那題兩組都做完，之後的題兩組都標「未實跑」；不因結果提前停止。
   - 安裝失敗，或答案沒有可執行的步驟時，該題其餘 [L2] 項目都記不過；這算實跑過。
   - 依 C6 判定為正確的「沒有工具符合」答案，該題不列入 D3。
8. **穩定性**：
   - 每題列出兩組 3 次的 L1 結果（例如 2/3）。
   - 「不穩定」＝該組三次 L1 不全相同，只在三次都有結果的題判定。
   - 兩組的不穩定題數只在兩組都有完整三次的題上比較，並寫明是幾題。
   - 只描述，不設門檻。補充重跑不做盲測偏好，也不標 E。

#### D. 成立門檻（都用第 1 次）

1. **主要主張**：中等＋困難 12 題中，（實驗組 L1 通過題數 − 對照組 L1 通過題數）**≥ 3**。報告列出實驗組贏與輸的題號。
2. **不退步**（照第 6 節「實驗組在這組不應該比對照組差」）：容易 8 題中，實驗組 L1 通過題數**不少於**對照組。並列出對照組過、實驗組沒過的題號。
3. **L2**：兩組都把所有 [L2] 項目跑完的題中，實驗組 L2 通過題數不少於對照組。這樣的題少於 6 題時，D3 記「未判定」。

### 9.3 開跑前追加：L2 的環境與固定項、評分者、揭露（2026-10-31）

本節和 9.1、9.2 一樣，是開跑前追加的事先登記，在任何一組開跑前 commit，commit 時間就是登記時間。它不改題目、檢查項目與 D 的門檻，只把第 5、8 節在 L2 的做法寫定；兩組、所有次數一體適用。念誠 2026-10-31 決定本節各項。文中的實測都在 2026-10-31 的 L2 沙盒做，紀錄在各題的 `calibration.md` 與 `eval/results/calibration/`。

#### A. 共同原則

#### B. Linux 的 L2 環境

1. **映像**：Modal Sandbox（x86_64，gVisor）。三個變體都從同一個以 digest 固定的 `ubuntu:24.04`（linux/amd64 `sha256:78d4744ead1f5b19b04d0df558ab182a5300903900755e515b2ca4d10eb2044d`）建出，Modal 不另外加 Python；紀錄在 `eval/results/l2-images.json`：

   - `base`：原樣。q03 用（它的檢查項目要求安裝後 `command -v python3 java node` 什麼都不印）。
   - `base-git`：只加 git。q10 用（它的檢查項目寫「base image (git only)」）。
2. **strace**（沒有對外連線的檢查要用）：`dev` 在任何答案執行前就裝在映像裡；`base`、`base-git` 只在答案的步驟全部跑完、開始檢查前才由評分者安裝。任何變體裡，strace 存在與否都不算答案的對或錯，任何檢查都不把它算進去。
3. **擋外連**（題目寫 with egress blocked 時）：用連 DNS 也擋住的方法，開跑前用 egress 自我測試證明：正向對照（網路開著時，查公開名稱、連公開位址都成功）、反向對照（擋住後兩者都失敗）、追蹤本身（`egress.py selftest` 抓得到連 TEST-NET、查 `.invalid` 名稱、背景程序稍後的連線）。DNS 擋不住時要照實寫明，那時以 strace 紀錄裡的查名稱次數判定（任何查名稱都算一次對外連線嘗試）。
   **結果**：Modal 沙盒裡 root 沒有 CAP_SYS_ADMIN，單純的 network namespace 不准建；`egress.py run --block-network` 改建 user＋network namespace（所有 uid、gid 對應成自己），裡面只有 loopback。正向對照：網路開著時公開位址連得到、DNS 會回答；反向對照：namespace 裡公開位址與 DNS 都失敗；strace 在 namespace 裡照樣記到每一次查名稱。所以採用 `--block-network`，DNS 也擋住，不需要退回 Modal 的擋網路（`eval/fixtures/_shared/calibration.md` 步驟 1、2）。每一次 `--block-network` 是新的 namespace，要互相連線的步驟（服務與它的用戶端）寫進同一個腳本、用一次跑完。沒有為了讓自我測試通過而放寬任何檢查。
4. **固定版本**：校準與 L2 用的工具（三個 agent CLI、Node.js、測試模型、Ollama、OpenCC 字典檔、字型、openai 與 srt 套件等）一律從官方來源下載到沙盒，以版本號與 sha256 固定，不 commit 進 repo；清單與 sha256 在 `eval/fixtures/PINS.md`（35 個檔在 dev image 沙盒下載後算 sha256，與來源公布的值 0 個不一致；之後 q19 換模型校準時另加 2 個 Ollama 模型，也在沙盒裡算過、相同；Docker 映像只記 digest）。
5. **CPU 與記憶體**（`_shared/calibration.md` 步驟 4）：Modal 的 `cpu=4` 給 4 個 CPU（`nproc` 4），`cpu=8` 給 8 個。記憶體 cgroup 是 v1：沒有峰值計數（`memory.peak`、`memory.max_usage_in_bytes`）、沒有 `memory.stat`、沒有 OOM 計數，只有 `memory.usage_in_bytes`；它跟著程序自己配置的記憶體走（配置 600 MiB 時 634 MB），不含讀檔的 page cache（`cat` 2 GB 的檔時最大 2.2 MB）。所以 `mem_peak.sh` 用每 0.2 秒取樣的 `usage_in_bytes`（`method` 記為 `sampled memory.current`）；比 0.2 秒還短的尖峰可能漏掉，報告照實寫明。超過硬上限時整個沙盒結束（Modal 回報 returncode 137），不是只有那個程序被 kill：這記為那一步被 OOM kill。
   - q03：照它的校準步驟 3，page cache 不計入 → 用規則 A（題目原文：memory.peak ≤ 1,000,000,000，以取樣值判定），沙盒 cpu=4、不設硬上限；不用規則 B 的硬上限。

#### G. 「git diff 改了幾行」的算法

q07（at most 3 changed lines）與 q09（changes at most 5 lines）用同一個算法（`eval/fixtures/_shared/git_diff_lines.py`）：先 `git add -A`，看 `git diff --cached -M` 相對於改動前的 commit，每個 hunk 取（刪掉的行數，加上的行數）較大者，所有 hunk 加總。原地改一行算 1 行；只搬移不改內容的檔算 0 行；二進位改動沒有行數，算不過。兩題的門檻不變（3 行、5 行）。
